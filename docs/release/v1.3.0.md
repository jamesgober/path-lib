# v1.3.0 - Owner and permission checks

`path-lib` 1.3 is a security release. The `App` methods that create directories now check every directory of the application that already exists, Windows global directories are no longer writable by every user, and secrets written with `write_atomic` are never in a file other users can open. The checks are public, so programs can run them on their own files.

```toml
[dependencies]
path-lib = "1.3"
```

## What changed

**Existing directories are checked.** `ensure`, `create`, `ensure_private`, and `create_private` used to accept any directory that already existed. In a shared parent (`%ProgramData%` for every global kind on Windows, `/var/tmp` for global temp, `/tmp` on macOS without `TMPDIR`) another user could create the directory first and own every file the application later wrote there. Now each existing directory of the application, from the kind it is nested in down to the one requested, must be owned by the current user or an administrator account and must not be writable by other accounts. `ensure_private` also requires the final directory to be unreadable by others. A directory that fails is refused with `Error::Refused` and a reason; it is never changed.

**Windows directories get an explicit list.** Global directories used to inherit the `%ProgramData%` list, which lets `Users` create files and folders inside. They now get a protected list: full control for the current user, `SYSTEM`, and `Administrators`, read and list for `Users`. User and portable directories get the private list, as `ensure_private` already did.

**Links in the middle of a sub-path are refused.** `create(kind, "a/b")` with a link or junction at `a` used to create `b` wherever the link pointed. Directories are now created one at a time, and a link at any level is refused.

**`write_atomic` stages at `0600` on Unix.** The temporary file is created exclusively with mode `0600` and receives the final mode only after the contents are written, so a secret is never in a `0644` file, even briefly. The owner and group of the replaced file are kept where the process may set them.

**`App::remove` no longer takes nested kinds with it.** On Windows cache, logs, state, and runtime live inside data, so `remove(Kind::Data, "")` deleted all of them. A path that is or holds another kind's directory is now refused; the new `App::clear(kind)` empties a directory and keeps the nested kinds.

**macOS user temp without `TMPDIR`** is the per-user directory from `confstr(_CS_DARWIN_USER_TEMP_DIR)`, not `/tmp`.

## New API

```rust
use path_lib::{App, Kind, Others};

// Refuse a directory or file with an untrusted owner, or that others can change.
path_lib::check_owner(&dir, Others::MayRead)?;
// ... or read.
path_lib::check_owner_private(&keys)?;

// Open a configuration file only if it passes, and read from that handle.
let file = path_lib::open_checked(&env_file, Others::NoAccess)?;

// Write a secret that is private from the first byte, new or existing.
path_lib::write_atomic_private(&env_file, "TOKEN=abc\n")?;

// Empty a kind's directory, keeping the kinds nested in it.
let removed = app.clear(Kind::Data)?;
```

| Check | Unix | Windows |
|---|---|---|
| Owner | effective user or root | current user, `SYSTEM`, or `Administrators` |
| `Others::MayRead` | no group or other write bit | no DACL entry grants another account a write right |
| `Others::NoAccess` | no group or other bit | no entry grants another account write or read |

Everything is read from an open handle and the final component is never followed. On Unix the handle is compared with the path's device and inode, and files are opened without blocking, so a FIFO is refused rather than hanging the caller. On Windows a directory's inheritable entries count too, and a volume without access control lists fails.

## Upgrading

A directory created by an earlier version that other accounts can write is now refused. The common case is a Windows global directory made by 1.2 or earlier. Delete it and let `ensure` create it again, or remove the access the error names.

`make_dir`, `make_file`, and the parents `write_atomic` creates are unchanged and unchecked: they take any path. Use the `App` methods or `check_owner` for directories that may be shared.

The crate still has no dependencies. The Unix owner check declares `geteuid` and the macOS temp lookup declares `confstr` directly, like the existing Windows bindings.
