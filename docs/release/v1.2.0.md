# v1.2.0 - File access on Windows

`path-lib` 1.2 added a check for configuration and secret files on Windows: whether any account other than the current user, `SYSTEM`, and `Administrators` can change or read an open file. It is an additive release: everything in 1.1 behaves exactly as before.

## What `path-lib` Is

Application and OS directory resolution for Linux, macOS, and Windows. `App` resolves the data, config, cache, logs, state, runtime, temp, and documents directories of one application for the current user, the whole machine, or one chosen folder. Sub-paths built on those directories are validated before they exist, and the filesystem operations refuse to overwrite, follow links, or delete critical paths. Zero runtime dependencies.

```toml
[dependencies]
path-lib = "1.2"
```

## New in 1.2.0

**`file_access(&file)`** returns a **`FileAccess`** for an open file. On Unix a program can refuse a configuration file another user can change by checking the mode and owner of the open descriptor. Windows had no such check in the crate, and it needs one: `%ProgramData%\<app>\config` lets every local user create files by default, so anyone on the machine can plant a `.env` or `.conf` there for a service running as `SYSTEM` to read.

```rust
use std::fs::File;

let file = File::open(&config)?;
let access = path_lib::file_access(&file)?;
if !access.enforced || !access.owner_trusted || access.others_can_write {
    return Err("another account can change the configuration".into());
}
// For a secret, also refuse `access.others_can_read`.
```

- **`enforced`:** the volume keeps access control lists. FAT, exFAT, and some network shares do not, and there anyone can change any file; the other fields then hold the unsafe answer, so a check that forgets `enforced` still refuses.
- **`owner_trusted`:** the owner is the current user, `SYSTEM`, or `Administrators`. An owner can always rewrite the list, so an untrusted owner can take the file over whatever the list says now.
- **`others_can_write` and `others_can_read`:** the DACL grants another account a right that changes the file (write, append, attributes, delete, permissions, ownership, generic write or all) or reads it (read data, generic read or all). `OWNER RIGHTS` is trusted exactly when the owner is. A NULL DACL reports both.

Everything is read from the handle, never from the path, so the file checked is the file read. Only allow entries that apply to the file are counted and deny entries are ignored: the answer can overstate what other accounts can do, never understate it. The security descriptor is parsed as a bounds-checked byte slice, and a malformed one fails with `InvalidData`. The cost is three system calls and one pass over the list.

The binding is hand-written like the existing ones (`GetVolumeInformationByHandleW`, `GetSecurityInfo`, `GetSecurityDescriptorLength`, `LocalFree`); the crate still has no dependencies. Tests set real access control lists on files (Everyone write, Everyone read, a NULL DACL) and read them back through `file_access`, and check every truncation of a descriptor is refused.

docs.rs now also builds the Windows target, where `file_access` is documented.
